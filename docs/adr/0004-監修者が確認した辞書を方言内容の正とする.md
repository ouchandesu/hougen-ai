# 0004: 監修者が確認した辞書を方言内容の正とする

- ステータス: Accepted
- 実装状況: 一部実装（辞書と放送の用例の読み書き、管理画面での編集、研修クイズの出題と調べるモードへの適用 — api/_dictionary.js, api/dictionary.js, api/quiz.js, api/lookup.js, admin.html。Supabase への SQL 適用は未検証 — 台帳 DB-372。使用頻度・時系列の表示、変換への適用は未実装）
- 決定: 方言の語・例文・意味・アクセント・使用頻度・用例は、方言の資料で裏付けた辞書に持ち、モデルの生成物は根拠の無いものとして区別する。語ごとの確認は資料に拠り、監修者は採否の方針を決める。辞書には放送素材の用例を番組名・放送日つきで保存する

## コンテキスト

調べる・研修・変換の内容は、モデルがその場で生成している。利用者は放送局で、読み聞かせやアクセント指導のように局の名前で外に出す使い方が要望にある。
モデルは、使用頻度（よく使う／マイナー）・アクセント・時系列の変化について根拠を持たない。
研修クイズでは、条件を指示しても、モデルが語の意味を作る問題が一定の割合で出た（出題の語をモデルに選ばせていた）。
監修者（プロジェクトの開発者本人）は伊予弁の細かな語義の専門家ではなく、語ごとの確認は資料で裏付けてほしいという方針を持つ。
放送局からは、番組の映像・切り抜きを用例として保存してよいと了承を得ている。

## 決定

1. 方言の内容の正は辞書とする。辞書の各項目は、意味を裏付けた資料の出典（URL など）を持つ。
   出典の無い項目は置かない。古い言葉も、資料にそう書かれていれば置き、使われ方として表示する。
2. 監修者は、何を載せるか・どの資料を信頼するかの方針を決める。個々の語の意味は資料に拠り、監修者の記憶で補わない。
3. モデルは辞書を土台に使う（出題・解説・採点の根拠として辞書の項目を渡す）。
   出題する語はモデルに選ばせず、辞書から選ぶ。辞書の意味と違う意味をモデルに作らせない。
4. 用例には出典（番組名・放送日・放送素材）を持たせる。時系列の分析は、この放送日から行う。
5. 辞書は Supabase に置く。スキーマは他のテーブルと同じくリポジトリの外で管理し、変更は SQL を人間が適用する。
   読み取りは公開済みの語だけを RLS で許し、書き込みは管理 API がサーバー側で管理者を確かめてから行う（ADR 0001 決定 3 と同じ方式）。
   リポジトリ内の一覧（`api/_vocab.js`）は、辞書の初期データの元と、Supabase が使えないときの予備として残す。

## 帰結

- 資料に載っていない語や、今の話し言葉としての自然さは辞書に入らない。放送の用例（決定 4）が入るまでは、辞書は既存の方言資料の範囲に留まる。
- 語を足すたびに資料を探す手間がかかる。資料どうしで意味が食い違う語は、監修者の方針で採否を決める。
- 使用頻度・アクセントの表示と、アクセントの自動判定（ADR 0005 の音声にも使う）は、この辞書ができるまで作れない。
- 放送素材そのものの保存先（Supabase Storage か、別のストレージか）と容量・費用は未決。月額予算の相談が済むまで、用例はまず文字起こしと出典情報で持つ。
- 語の `id` は学習記録が参照するので、辞書でも変えない（管理画面でも保存後は変えられない）。
- Supabase が使えない間は予備の一覧に切り替わるため、管理画面で直した内容はその間反映されない。予備の一覧は管理画面での変更に追随しない（台帳 API-718）。
- 解説の文章そのものはモデルが生成するため、辞書の意味を渡しても、細部に根拠の無い記述が混ざる余地は残る。

## 却下案

- モデル生成のまま注意書きを付ける: 頻度・アクセント・時系列に根拠が無く、放送局の名前で出せない。
- 出題の語をモデルに選ばせ、条件で縛る: 条件を強めても、意味を作る問題が無くならなかった。
