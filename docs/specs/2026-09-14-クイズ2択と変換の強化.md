# クイズの 2 択形式と、変換の部分選択・濃さ・言い換え候補

南海放送からの要望（2026-09-14 に整理）のうち、フェーズ 1「今の構成のままできるもの」。
音声・発音判定・放送データ辞書は先方への確認待ちで、この spec の範囲外（末尾の Non Goals）。

## 目的

- **研修（アナウンサー）**: 単語の意味を書かせるだけでなく、**例文**を読んで 2 択で答えられる。
  2 択は「意味を当てる」「使う場面を当てる」の 2 種類。今の記述式は残し、形式を選べる。
- **変換（アナウンサー）**: 変換結果を丸ごと受け取るのではなく、
  - 変わった箇所ごとに「伊予弁にする／標準語のまま」を選べる（部分変換）
  - 箇所ごとに言い換え候補から選べる
  - 方言の濃さ（軽め／ふつう／濃いめ）を変換前に選べる

## 範囲

### 研修モード

- 設定カードに「出題形式」を足す: `記述式`（今のまま）/ `2択・意味` / `2択・場面` / `2択・ミックス`（意味と場面を交互）。
- 2 択の出題は新しい action `generate_choice`（`kind: 'meaning' | 'scene'`）。1 回の呼び出しで問題・選択肢・正解・解説まで返す。
- 回答はボタン 2 つ。押したらその場で正誤と解説を出す（採点 API を呼ばない）。
- 採点結果カード・最終結果・学習記録は記述式と共用する。2 択の結果は `correct` / `incorrect` の 2 値。

### 変換モード

- 入力カードに「方言の濃さ」: `軽め`（語尾・助詞まで）/ `ふつう`（今の挙動）/ `濃いめ`（語彙も積極的に）。既定は `ふつう`。
- 結果の本文は、変わった箇所をチップとして表示する。チップを押すと「伊予弁 ⇄ 標準語」が切り替わる。
- 対応表の各行に、言い換え候補（伊予弁の別表現）があれば選べるようにする。選んだ表現が本文に反映される。
- 組み上がった本文をコピーするボタンを付ける（部分変換した結果を原稿に貼るのが使い道なので）。

## 触る境界（Large 領域）

- **API とフロントの JSON 契約**: 当たる。`api/quiz.js`・`api/convert.js` のプロンプト内 JSON 例と `index.html` の描画側を両方変える。
- 認証: 当たらない（既存の `verifyAuth` をそのまま通す）。
- Supabase: スキーマは変えない。`training_records.details`（jsonb）に入れる 1 問ぶんの中身に `format` などのキーが増えるだけ。
- 対象方言: 当たらない（`TARGET_REGION` とプロンプト共通ルールを使う）。
- 利用ログ: action `quiz_generate_choice` が増える → `admin.html` の `actionLabels` に足す。

## 契約（新旧）

### `POST /api/quiz` `action: 'generate_choice'`

リクエスト: `{ action, kind: 'meaning'|'scene', usedWords, region }`

モデルに出させる形（プロンプト内 JSON 例）:

```json
{
  "sentence": "伊予弁の例文",
  "region": "県内の地域名",
  "question": "問い",
  "correct": "正しい選択肢",
  "wrong": "もっともらしいが誤りの選択肢",
  "explanation": "解説",
  "announcerTips": "アナウンサーとしての注意点"
}
```

API が返す形（サーバーで正規化）:

```json
{
  "kind": "meaning",
  "sentence": "…", "region": "…", "question": "…",
  "choices": ["…", "…"],
  "answerIndex": 0,
  "explanation": "…", "announcerTips": "…"
}
```

### `POST /api/convert`

リクエスト: `{ text, level: 'light'|'normal'|'strong' }`（`level` 省略時は `normal`）

モデルに出させる形:

```json
{
  "segments": [
    { "text": "変わらない部分" },
    { "standard": "標準語の部分", "iyoben": "伊予弁の表現", "alternatives": ["別の伊予弁表現"] }
  ]
}
```

API が返す形: `{ segments, converted }`。`converted` はサーバーが全部伊予弁側で連結したもの。
今の `mappings` は返さない（`segments` から導けるので二重に持たない）。

## 自分で判断した箇所

- **2 択の選択肢の並びはサーバーで乱数シャッフルする。** モデルに `choices` と `answerIndex` を直接書かせると、
  正解が 1 番目に偏りやすい。`correct` / `wrong` を分けて出させ、並べ替えはコードでやる。
- **2 択の正解を出題レスポンスに含め、採点はブラウザで行う。** 開発者ツールで正解が見えるが、
  研修用で不正の動機が薄く、1 問あたり API 呼び出しが 1 回減る（費用と待ち時間が半分）ほうを取った。
- **変換は `converted` + `mappings` をやめて `segments`（順番つきの区切り）にする。**
  今のハイライトは `converted` の中を `iyoben` の文字列で探しており、同じ表現が 2 回出る・短い語が長い語に含まれる
  とずれる。部分変換で本文を組み立て直すには、区切りの位置が確定している必要がある。
- **`segments` の標準語側を連結して入力文と一致しないときも、結果は出す。** モデルが句読点や空白を変えることがあり、
  一致しないたびにエラーにすると使えない。一致しない場合は画面に「原文と一部異なります」の注記を出す。
- **2 択・ミックスは乱択でなく交互。** 5 問でも両方が必ず出るように。
- **学習記録の一覧表示は変えない。** 形式ごとの内訳は `details` に残すだけにする（表示を増やす要望はまだない）。
- ADR は書かない。今回の判断はどれも契約の中身で、コードとプロンプトの JSON 例に残る。
  「放送局の名前で出す内容を誰が監修するか」「音声の方式」は先方の回答後に ADR にする。

## Non Goals

- **使用頻度（マイナー／よく使う）の表示**: 監修者が決まるまで出さない。AI の推測を頻度として出すと根拠のない表示になる。
- **東予・中予・南予の選択**: ADR 0003（方言は 1 つ）の見直しになる。
- **2 択の中身「正しい伊予弁を当てる」**: 今回の選択に入らなかった。
- **音声（読み上げ・ウィット）、マイクでの発音・アクセント判定、放送データからの辞書・時系列**: 南海放送への確認待ち。
  確認事項: 監修者の有無 / 音声の方式とウィットの声の権利 / 利用者の範囲（局内か、保育園・小学校にも出すか）/
  放送素材を用例として保存してよいか / 音声合成やサーバーの月額予算。
- Anthropic のモデル ID の直書き（台帳 API-293）はこの PR では触らない。

## ファイルごとの作業

1. **`api/quiz.js`**
   - `action === 'generate_choice'` の分岐を追加。`kind` が `meaning` / `scene` 以外なら 400。
   - プロンプトは `purityRule()` / `jsonOnlyRule()` を使う。`meaning` は「例文の標準語訳」、`scene` は「その言い回しが使える場面・相手」を選ばせる。
     誤りの選択肢は「標準語話者が取り違えそうな、もっともらしいもの」と指示する。
   - モデル出力を正規化する関数（`correct` / `wrong` → `choices` + `answerIndex`、乱数は引数で差し替え可能）を
     `_` 始まりの共有ヘルパーに置き、テストから呼べるようにする。必須キーが欠けたら 500（「もう一度お試しください」）。
   - ログの action は既存の `'quiz_' + action` のまま（→ `quiz_generate_choice`）。
2. **`api/convert.js`**
   - `level` を受け取り、濃さごとの指示文を 1 か所の対応表から差し込む。未知の値は `normal` に丸める。
   - プロンプトの JSON 例を `segments` に変える。`naturalnessRule()` は `light` / `normal` で入れ、`strong` では弱めた文面にする。
   - モデル出力の正規化（区切りの型の判定、`alternatives` を文字列配列に丸める、`iyoben` と同じ候補の除去、`converted` の連結、
     標準語側の連結が入力と一致するかのフラグ `matchesInput`）を共有ヘルパーに置く。
3. **`index.html`**
   - 研修: 出題形式のセレクト、2 択の問題表示（例文・問い・ボタン 2 つ）、押したら採点カードへ。
     `showQuizPhase` に 2 択の問題カードを足す。`answers` の要素に `format` / `kind` / `choices` / `userChoice` を足す。
     最終結果の「振り返り」は `word` の代わりに `sentence` を出せるようにする。
   - 変換: 濃さのセレクト、`segments` からの本文描画（チップで伊予弁 ⇄ 標準語）、対応表の候補セレクト、コピーボタン、
     `matchesInput === false` の注記。`buildHighlightedText` は `segments` 描画に置き換えて消す。
4. **`admin.html`**: `actionLabels` に `quiz_generate_choice: '研修（2択出題）'` を足す。
5. **`scripts/checks/`**
   - 正規化ヘルパーの単体テスト（シャッフル後も `choices[answerIndex]` が `correct`、欠損時に例外、`segments` の連結と `matchesInput`）。
     冒頭には「これが無いと、正解の位置がずれた問題や組み立てを誤った本文が、エラーなしで画面に出る」と書く。
   - JSON 契約の突き合わせ: プロンプトの JSON 例のキーと、正規化ヘルパーが読むキーが一致すること。
     冒頭には「プロンプトと描画側のキーが片方だけ変わっても何も落ちない」（全体ルールの地雷）と書く。
