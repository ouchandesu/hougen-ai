# 辞書を Supabase へ移し、管理画面から語と放送の用例を登録できるようにする

フェーズ 2（ADR 0004）の最初の範囲。今は研修クイズの出題語が、リポジトリ内の一覧（`_vocab.js`、40 語）にだけある。

## 目的

- **管理者（開発者本人）**：デプロイせずに、管理画面から語を足す・直す・公開できる。
  資料で裏付けた語だけを公開する決まり（出典 2 つ以上）は、画面の入力チェックとサーバーの検証の両方で守る。
- **管理者**：放送番組の用例（番組名・放送日・発言の文字起こし・標準語訳・切り抜きの URL）を、語にひもづけて登録できる。
- **アナウンサー**：
  - 調べるモードで、入力した語が辞書にあれば「資料より」のカードが出る（資料の意味・出典・放送での用例）。
  - AI の解説も、辞書の意味を「正」として書かれる。
- **研修クイズ**：出題語を Supabase の辞書（公開済みの語）から選ぶ。Supabase が使えないときは、今の一覧に切り替えて動き続ける。

## 範囲

### Supabase（SQL は人間が適用する）

- **テーブル `dialect_entries`**：語 1 件＝1 行。
  - 列：`id`（今の一覧の id を引き継ぐ）/ `word` / `meaning` / `region` / `usage` / `note` / `examples`（jsonb）/ `sources`（text[]）/ `status`（`draft` | `published`）/ 作成・更新の日時と更新者
- **テーブル `broadcast_examples`**：放送の用例 1 件＝1 行。
  - 列：`entry_id` / `program` / `aired_on`（放送日）/ `transcript`（発言）/ `standard`（標準語訳）/ `clip_url` / `clip_start_sec` / 作成日時と作成者
- **RLS**：
  - 読み取り：公開済みの語と、公開済みの語の用例だけを、anon と authenticated に許す。
  - 書き込み：ポリシーを作らない。管理 API がサーバー側で is_admin を確かめてから service_role で書く（`api/admin.js` と同じ方式）。
- **初期データ**：今の 40 語を `published` で入れる INSERT 文を、スクリプトで一覧から生成する。

### API

- **辞書の読み出しヘルパー（新規、api 配下の `_` 始まり）**：
  - 公開済みの語を anon key で読む。関数インスタンス内で 5 分キャッシュする。
  - 失敗したとき・Supabase が未設定のときは、今の一覧に切り替える。
  - 語の検証（出典 2 つ以上・URL の形・例文の出典が出典一覧にあること）もここに置き、今の一覧のテストと管理 API の両方で使う。
- **`api/quiz.js`**：出題語の出どころを、上の読み出しヘルパーに変える。応答の形は変えない。
- **`api/lookup.js`**：
  - 入力が辞書の語と一致したら、プロンプトに辞書の意味を「正」として渡す。
  - 応答に `vocab`（研修と同じ形）と `broadcastExamples`（放送日の新しい順、最大 5 件）を足す。
- **管理 API（新規）**：辞書の一覧（下書きも含む）、語の追加・更新・公開、放送の用例の追加・削除。
  - 認証は `api/admin.js` と同じ（ログイン必須、サーバー側で `profiles.is_admin`）。
  - 管理者の確認処理は `api/_auth.js` に切り出し、`api/admin.js` と共用する。

### 画面

- **`admin.html`**：「辞書」の節を足す。
  - 語の一覧（状態・語・意味・出典の数・用例の数）
  - 語の追加・編集フォーム（出典は 1 行 1 URL、例文は「方言 ＝ 標準語 ＝ 出典 URL」を 1 行ずつ）
  - 公開・下書きの切り替え
  - 語ごとの放送の用例の登録と一覧
- **`index.html`**（調べるモード）：辞書にある語なら「資料より」のカードを出す。
  - 中身は、語・意味・地域・使われ方・補足・出典、放送での用例（番組名・放送日・発言・標準語訳・切り抜きへのリンク）。

## 触る境界（Large 領域）

- **Supabase のスキーマ・RLS**：当たる。テーブル 2 つとポリシーを足す。SQL を PR に貼り、人間が適用する。
- **認証と権限**：当たる。管理者の確認処理を `api/_auth.js` に切り出す（振る舞いは変えない）。新しい管理 API も同じ確認を通す。
- **service_role key の使い道**：増える。新しい管理 API が辞書テーブルへ書き込む。フロントへ出る経路（`api/config.js`）には混ぜない。
- **JSON 契約**：当たる。`api/lookup.js` の応答に `vocab` と `broadcastExamples` を足す。研修の応答は変えない。

## 自分で判断した箇所

- **読み取りは anon key と RLS、書き込みは管理 API と service_role に分ける。**
  管理者の書き込みを RLS のポリシーで許す方式は、`profiles` のポリシーがリポジトリから見えず（台帳 DB-164）、正しさを確かめられない。
  今の管理画面と同じ「サーバーで is_admin を確かめてから service_role」にそろえる。
- **出典は 2 つ以上を必須にする。** 監修者の方針（資料で 2 つ以上の裏付け）を、テーブルの CHECK 制約、サーバーの検証、今の一覧のテストの 3 か所で同じ条件にする。
- **Supabase が使えないときは今の一覧に切り替える。** 辞書の読み出しが止まってもクイズが止まらないようにする。
  その代わり、管理画面で直した内容が、切り替え中は反映されない。一覧は「初期データの元」と「非常時の予備」として当面残す。
- **切り抜きは URL だけを持つ。** 映像ファイルの保存先は予算の相談待ち（ADR 0004 帰結）。
- **使用頻度と時系列の表示はまだ作らない。** 用例が数件しか無い状態で「よく使う」「増えている」と出すと、根拠の無い表示になる。
  用例の件数と放送日の範囲をカードに出すところまでにする。
- **変換モードには辞書を使わない。** 変換は語単位の置き換えでなく文全体の自然さを優先しており、辞書の語を差し込む方式は別に設計が要る。
- ADR は新しく書かない。ADR 0004 の決定 5 の実装で、実装状況の行を更新する。

## Non Goals

- 使用頻度・時系列の変化の表示（用例が溜まってから）
- 変換モードへの辞書の適用
- 切り抜き映像のアップロードと保存
- 監修者以外の入力者（テロップ担当など）向けの権限や画面
- 音声（フェーズ 3）

## ファイルごとの作業

1. **辞書の読み出しヘルパー（新規）**：`loadPublishedEntries()`（キャッシュ・予備への切り替え）、`findByWord()`、`validateEntry()`、Supabase の行を今の一覧と同じ形に直す関数。
2. **`api/_vocab.js`**：
   - 検証を読み出しヘルパーの `validateEntry` に寄せる。
   - 一覧は「初期データ・予備」とコメントで明記する。
3. **`api/quiz.js`**：出題語の選択を、`await loadPublishedEntries()` の結果から行う（`pickEntry` / `findEntry` に一覧を渡す）。
4. **`api/_auth.js`**：`verifyAdmin(req)` を足す（トークン → ユーザー → `profiles.is_admin`）。`api/admin.js` はそれを呼ぶように変える。
5. **管理 API（新規）**：GET 一覧、POST 語の保存（`validateEntry` を通す）、POST 用例の追加、DELETE 用例。書き込みは Supabase REST の upsert と insert。
6. **`api/lookup.js`**：辞書と一致したら、プロンプトに資料の情報を渡し、応答に `vocab` と `broadcastExamples` を足す（用例は anon key で読む）。
7. **`admin.html`**：「辞書」の節（一覧・フォーム・用例）。
8. **`index.html`**：調べるモードに「資料より」のカード。研修の採点カードの描画を共用する。
9. **初期データの SQL を生成するスクリプト（新規、scripts 配下）** と、`package.json` の `dict:seed-sql`。
10. **`scripts/checks/`**：
    - `validateEntry` の単体テスト
    - Supabase の行 ⇄ 一覧の形の変換テスト
    - 読み出しヘルパーが失敗時に予備へ切り替えることのテスト（fetch をスタブ）
    - lookup の JSON 契約（`vocab` / `broadcastExamples`）の突き合わせ
    - 管理 API が `verifyAdmin` を通ることの検査（未認証の分岐が先にあること）

## 人間が適用する SQL（PR に貼る）

- テーブル 2 つ、CHECK 制約（`usage` の値、`status` の値、`cardinality(sources) >= 2`）、`updated_at` の更新トリガ、RLS の有効化と読み取りポリシー。
- 初期データ（`npm run dict:seed-sql` の出力）。

## 検査

- 編集ごとに構文フック。`npm test`。
- **手元（スタブ）**：API ハンドラを動かし、Supabase と Anthropic の fetch をスタブにする。そのうえで管理画面の保存・検証エラー・用例の登録、調べるモードのカードを通す。
- **プレビュー（実サービス）**：SQL の適用後に、管理画面から語を 1 件足して公開する。研修で出題されること、調べるモードでカードが出ることを確かめる。

## 手元で検証できないもの

- RLS の実際の効き方（anon で下書きが読めないこと）。適用後に、anon key で下書きを select して 0 件になることをプレビューで確かめる。
- `profiles.is_admin` が、あなたのアカウントで true になっているか。Supabase ダッシュボードで確認してもらう。
