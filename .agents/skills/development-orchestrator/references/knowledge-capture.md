# 知識の行き先と PR の仕上げ（ステップ 8〜9）

## 学びに専用の文書を作らない

行き先は 5 つのどれか。

- **コードコメント** — 既定。読み手にその疑問が浮かぶ場所に書く。
- **テスト** — 守る価値のある不変条件は、散文ではなく `scripts/checks/` のテストにする。
- **ルール** — `.agents/rules/`。複数のタスクで再発した見落としだけ。
  まず**最も一般的な形**で書いてから、「その 1 行を置く価値があるか」を問う。
  **ツリーの中に同じ壊れ方をする 2 つ目の場所を名指しできるときだけ**価値がある。
  1 箇所しかない学びはコメントと ADR がすでに持っていて、ルールは 3 つ目の写しになる。
  ルールは全セッションの全ターンに載る。予算はテスト（`scripts/checks/agent-rules.test.js`）が守る。
- **ADR** — アーキテクチャ方針が実際に変わったとき（`docs/adr/README.md` の運用ルール）。
- **どこにも書かない** — 正直で、いちばん多い答え。

## やらなかったことの台帳へ収穫する

`docs/adr/未対応実装/` へ次を移す:

- spec の Non Goals
- 実装中に見つけて意図的にやらなかったこと
- 未検証のまま残したもの（鍵が無い・Supabase に触れない）
- 新しく必要になった手作業（Vercel 環境変数の追加、Supabase への SQL 適用など）

## PR の仕上げ

- 検証コマンドの出力を貼る。
- `## plan からの逸脱` の節（autonomy-and-checkpoints.md）。
- 人間が手でやる必要があること（デプロイ、環境変数、SQL 適用）を箇条書きで最後に置く。
- `docs/specs/` の該当ファイルを消す。
- Draft を解除する。マージは人間がやる。
