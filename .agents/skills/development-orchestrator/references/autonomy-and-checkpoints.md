# 自律と確認

全ステップに効く。フローの最初に読む。

## 承認ゲートは実装開始の 1 回だけ

- plan を提示して「実装を始めていい?」と訊き、明確な了承まで実装コードを書かない。
  了承後は最後までゲート無しで走る。
- **書き上げた spec の承認で止まらない。** spec を書いたらコミットして、同じターンで PR まで進む。
  自分で判断した箇所は理由つきで spec に書いて先へ進む。異論は段階 4 で出る。

## 実装中に見つかった plan の誤りは、訊かずに決めて進む

呼び出し漏れ、想定と違うライブラリや API の挙動、書けないテスト、より安い構造 —— どれも質問に見えるが止まらない。
「訊いていたら推したはずの案」を採って実装を続け、**完了時にまとめて報告する**。

- 報告は PR の完了報告の独立した節（`## plan からの逸脱`）に書く。散文に埋めない。
- 各件について **plan が何と言っていたか / 代わりに何をしたか / なぜか** を書く。
- 1 回のまとめ報告が N 回の中断に勝つ。人間は動くコードを前に一括で見られて、どの 1 件も安く覆せる。

## それでも止まって訊くもの（plan の変更ではない）

- 破壊的・不可逆な操作、外部へ出る操作。このレポジトリでは特に:
  - デプロイ（`vercel` 系）、Vercel 環境変数の変更
  - `main` への push、履歴を書き換える push
  - Supabase のテーブル・RLS・RPC の変更、本番データへの書き込み・削除
- 推測を外すと成果物が「劣る」ではなく「無意味」になるほど曖昧な要件
- **spec の決定自体が間違っていると分かったとき。** 承認された設計が無効になる

## スコープを黙って縮めない

「どうやるか」は自分の裁量、「少なく届ける」判断は人間のもの。
一部が詰まったら残りを全部やり切って、何を落としたかを明言する。

## 外部サービスの資格情報が無いのは通常状態で、ブロッカーではない

手元には `ANTHROPIC_API_KEY` も Supabase の鍵も無いのが普通。止まって訊かない。

- 契約を仮定して実装し、仮定の根拠を強い順に置く:
  **(1) ベンダの型定義や SDK (2) 今取得したドキュメント（記憶から書かない） (3) 実データでの検証 (4) 本当の当て推量**。
  (4) なら**コメントにそう書く**。
- 境界で自前の形へ正規化して、外したときの修正を 1 関数に閉じる
  （例: Anthropic のレスポンスから JSON を取り出す箇所、Supabase REST の行の取り出し）。
- スタブで経路を通す。鍵が無いことは経路を通さない言い訳にならない。
- **スタブで通ったものを実サービスで動いたと書かない。** 未検証として PR と `docs/adr/未対応実装/` に残す。
